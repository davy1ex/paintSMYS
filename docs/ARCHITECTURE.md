# paintSMYS Architecture

**Статус:** целевая архитектура; перед реализацией сверить с текущим репозиторием и сохранить работающие решения.  
**Архитектурный стиль:** модульный монолит с Ports & Adapters.  
**Клиенты:** общий React Editor для Electron Desktop и Browser Web App.  
**Принципы:** local-first, file-system-first, extensible-by-design.

## 1. Назначение

paintSMYS — объектный графический редактор с эстетикой Microsoft Paint / Windows 95. Он сначала поставляется как локальное Desktop-приложение, но общие Core и Editor UI должны допускать запуск в браузере. Документ сцены является источником истины для редактора. UI, Electron, Web и будущие плагины обращаются к сцене через общие типы и операции, а не реализуют собственные правила изменения объектов.

Архитектура должна поддерживать законченный Desktop-путь пользователя: создать проект, редактировать сцену, сохранить проект в папку, закрыть и снова открыть его. Общий редактор также должен собираться как Web App. Для цифрового сада предусмотрен отдельный лёгкий Web Viewer, который читает опубликованную сцену и её ресурсы. Импорт и экспорт добавляются после основного пути. Plugin API и управление через MCP остаются будущими направлениями.

## 2. Архитектурные принципы

1. **Проект — директория на диске.** В ней находятся `project.json` и `assets/`. Отдельная база проектов и скрытый каталог проектов не нужны.
2. **SceneDocument — источник истины сцены.** React, Electron и плагины не должны содержать отдельную реализацию правил изменения объектов.
3. **Document Core независим от платформы.** Это TypeScript-код без React, Electron и DOM.
4. **Общий Editor UI не знает о платформе.** Один React Editor может быть запущен из Desktop и Web entrypoints. В общих компонентах нет `window.electronAPI` и прямых обращений к браузерным файловым API.
5. **Платформы подключаются через узкие интерфейсы.** Desktop и Web предоставляют только необходимые редактору операции; общего всеобъемлющего объекта `platform` не создаётся.
6. **Vite — инструмент сборки, не архитектурный слой.** Desktop и Web могут иметь разные Vite entrypoints и собираться независимо.
7. **FSD организует React UI, а не всё приложение.** FSD не требует массового перемещения файлов.
8. **Use Case координирует операции через несколько границ.** Чистые операции Core не оборачиваются в отдельный Use Case без необходимости.
9. **Рабочий код сохраняется.** Структура каталогов сама по себе не является поводом для переписывания или рефакторинга.
10. **Реализация идёт вертикальными сценариями.** Инфраструктура появляется вместе с пользовательскими возможностями, которым она нужна.

## 3. Модули и направление зависимостей

```text
Browser ───────────────┐
                       ├──→ index.html → src/app/web/main.tsx
Electron Main → Window ┘                    ↓
                                     src/app/App.tsx
                                             ↓
                                   src/editor/workspace
```

Целевая начальная структура:

```text
src/
├── app/
│   ├── desktop/
│   │   ├── main.ts
│   │   └── preload.ts
│   ├── web/
│   │   └── main.tsx
│   └── App.tsx
├── editor/
│   └── workspace/
│       ├── EditorWorkspace.tsx
│       └── editor-workspace.css
├── core/          # Document Core появится по мере реализации
└── application/   # Use Cases появятся по мере реализации

index.html
vite.config.ts
electron.vite.config.ts
dist/             # генерируемые сборки, не коммитятся
```

В `dist/` Desktop-сборка разделена на `main/`, `preload/` и `renderer/`; Browser-сборка находится в `web/`.

Это небольшая стартовая схема. `core/` и `application/` добавляются вместе с первыми сценариями, которым они нужны; заранее создавать пустые слои не требуется.

Один корневой `index.html` монтирует `src/app/web/main.tsx`, который запускает общий `src/app/App.tsx`. Electron Main открывает этот же UI локально; preload ограниченно передаёт необходимые Desktop-возможности. Общие React-компоненты не обращаются к Electron API. `vite.config.ts` и `electron.vite.config.ts` задают независимые Browser и Electron сборки.

Если позже появятся Project Use Cases, они будут зависеть от узких интерфейсов хранения и диалогов. Electron-адаптер останется за границей preload/Main, браузерные операции — за границей Web entrypoint. Для этого не требуется заранее вводить общий `platform` объект или отдельную папку платформ.

## 4. Document Core

Core содержит модель сцены и чистые операции над ней:

- `SceneDocument`, Artboard и типы объектов;
- валидацию документов;
- операции добавления, изменения и удаления объектов;
- операции изменения свойств Artboard;
- сериализацию и десериализацию сцены.

Примеры операций:

```ts
addRectangle(document, rectangle)
updateRectangle(document, id, patch)
removeObject(document, id)
updateArtboard(document, patch)
```

Операции иммутабельны и возвращают новый корректный документ либо явную ошибку. Они не читают файловую систему и не знают о состоянии интерфейса.

`TextObject` хранит исходное содержимое в `text`. Необязательные `runs` задают только цвет диапазонов по UTF-16 offsets (`start` включительно, `end` исключительно); диапазоны отсортированы, не перекрываются и не делят surrogate pair. Текст и runs остаются одним объектом сцены. При ручном изменении текста runs сбрасываются, потому что старые offsets больше не гарантированно соответствуют содержимому. Undo восстанавливает прежний текст вместе с runs; повторное применение подсветки пока выполняется вызывающим кодом.

Завершённое пользовательское действие должно превращаться в одно изменение документа. Например, жест Drag обновляет объект после завершения перемещения. Это правило создаёт основу для Undo/Redo.

## 5. Три вида состояния

### SceneDocument

Модель сериализуемой сцены:

- ID сцены;
- Artboard: ширина, высота и цвет фона;
- объекты и их свойства;
- ссылки на ресурсы сцены.

### ProjectSession

Состояние открытого проекта и сохранения. Концептуальная форма:

```ts
type ProjectSession = {
  document: SceneDocument;
  projectRoot: string | null;
  isDirty: boolean;
};
```

Сессия может содержать и другие данные, нужные для временных ресурсов и файловых операций. `projectRoot` и `isDirty` не сериализуются в `SceneDocument`. Изменение документа или ресурсов помечает сессию как dirty.

### Editor UI State

Временное состояние интерфейса, которое не входит в документ сцены:

- активный инструмент и выбранный ID объекта;
- текущий жест Drag и preview создаваемого объекта;
- открытые панели;
- масштаб и положение viewport, когда они появятся.

Видимость Inspector — настройка приложения, а не проекта.

## 6. Application Layer

Application координирует сценарии, затрагивающие несколько компонентов: сессию, Core, хранилище, Asset Storage и обработку ошибок.

Use Cases оправданы для:

- открытия проекта;
- Save и Save As;
- импорта ресурса;
- закрытия или замены проекта с защитой несохранённых изменений.

Операции Core вроде `removeObject` остаются чистыми операциями и не получают обёртку Use Case только ради дополнительного слоя.

## 7. Хранение проекта

Проект переносится как единая директория:

```text
my-project/
├── project.json
└── assets/
    ├── image-001.png
    └── logo.svg
```

`project.json` содержит идентификатор формата, версию формата, метаданные проекта и сериализованную сцену. На первом этапе поддерживается одна сцена. Формат, используемый стартовым сценарием:

```json
{
  "format": "paintSMYS",
  "formatVersion": 1,
  "project": {
    "id": "project-001",
    "name": "My Project"
  },
  "scene": {
    "schemaVersion": 1,
    "id": "scene-001",
    "artboard": {
      "width": 1920,
      "height": 1080,
      "backgroundColor": "#ffffff"
    },
    "objects": []
  }
}
```

`scene.schemaVersion` задаёт версию схемы `SceneDocument`. Текущая схема поддерживает Artboard и прямоугольные объекты; Document Core проверяет размеры Artboard (не более 16 384 px на сторону и 100 000 000 px общей площади), структуру объектов и цвета. Новые типы объектов и изменения сериализации требуют новой совместимой схемы.

Правила формата и операций:

- формат проекта и схема сцены имеют явные версии;
- пользовательские ресурсы хранятся внутри `assets/` и ссылаются переносимым способом;
- абсолютные пути исходных пользовательских файлов не сериализуются;
- загрузчик отклоняет относительные пути, выходящие за пределы Project Root;
- манифест записывается безопасно, чтобы ошибка сохранения не портила предыдущую исправную версию;
- повреждённый или несовместимый проект выдаёт понятную ошибку и не должен терять текущую открытую сессию.

### Project lifecycle

- **New:** создаёт несохранённую сессию; выбор папки не требуется.
- **Open:** получает папку через системный диалог, проверяет `project.json`, версию, данные и ссылки на ресурсы, затем открывает документ.
- **Первый Save:** пользователь задаёт родительскую папку и имя проекта; приложение создаёт внутри папку проекта.
- **Повторный Save:** записывает изменения в текущий Project Root.
- **Save As:** создаёт независимую копию проекта вместе с необходимыми ресурсами.
- **Close / замена сессии:** при dirty state предлагает Save / Don’t Save / Cancel. Отмена диалога, ошибка диска и отказ от сохранения не должны терять активный документ.

### Asset Storage

При импорте изображения приложение проверяет формат, копирует файл внутрь `assets/` и создаёт объект сцены со ссылкой на внутренний ресурс. Сцена не должна зависеть от файла в Downloads или Desktop.

Для несохранённой сессии позже потребуется временное хранилище ресурсов, управляемое приложением. При первом Save ресурсы копируются в новую директорию проекта. Эту инфраструктуру не нужно строить заранее — она появляется в вертикальном срезе импорта.

## 8. Границы Desktop и Web

В начальной структуре Electron Main и preload находятся в `src/app/desktop`. Renderer не получает произвольный доступ к Node.js filesystem. Electron Main отвечает за системные диалоги и операции с файлами; preload предоставляет только конкретные необходимые операции. `ipcRenderer` целиком в React UI не передаётся.

Browser entrypoint работает с возможностями браузера. Для выбора файлов или директорий позже может использоваться File System Access API в поддерживаемых браузерах либо другой механизм загрузки и сохранения. Web не предполагает свободного доступа к файловой системе, эквивалентного Electron.

### PNG export

Editor и PNG Export используют один `SceneSvgContent`: фон Artboard и объекты сцены задаются SVG-атрибутами, а selection и drag preview остаются отдельными UI-слоями. Export сериализует только это содержимое в SVG с размерами Artboard, затем создаёт PNG через Canvas. В Desktop Renderer передаёт ограниченный PNG payload через preload, а Electron Main показывает Save Dialog и записывает файл. Web создаёт временный Blob URL и запускает стандартное скачивание браузера. Export не меняет `SceneDocument`, историю или saved baseline.

При запуске Web App из WSL в браузере Windows файловый диалог остаётся частью браузера Windows. WSL-файлы видны через UNC-путь `\\wsl.localhost\<Distro>\...`; браузер может отклонить такую папку как содержащую системные файлы. Для Web-сценария проект можно открыть из папки на Windows-файловой системе. Для работы с проектом, который хранится в WSL, используй Desktop-адаптер и Linux-путь.

Когда появятся сценарии Open/Save/Import, они будут принимать узкие зависимости:

```text
Use Case → узкий Port ← Electron Adapter → preload → Electron Main → File System
             ↑
        Web Adapter → Browser APIs
```

Интерфейсы и адаптеры добавляются вместе с этими сценариями, а не как заранее построенный универсальный слой. Общий `EditorWorkspace` не получает глобальный объект возможностей платформы.

## 9. Общий Editor UI и FSD

`src/app/App.tsx` — общий React App. Он собирает UI из `src/editor`; текущий `EditorWorkspace` используется и Browser entrypoint, и Electron Renderer. Различия доступа к файлам появятся внутри Application Use Cases и адаптеров, когда эти сценарии будут реализованы.

```tsx
<EditorWorkspace document={session.document} onChange={updateDocument} />
```

Общие компоненты не обращаются к `window.electronAPI`, Node.js или браузерным файловым API. `src/app/web/main.tsx` только монтирует общий App; `src/app/desktop/main.ts` отвечает за Electron-окно.

FSD используется внутри React UI там, где помогает организовать пользовательские сценарии. Например:

- `features/new-project`, `features/open-project`, `features/save-project`;
- `widgets/property-inspector`, `widgets/project-summary`;
- `pages/welcome`, `pages/editor`.

Feature — сценарий, а не кнопка. Сохранение должно вызываться одинаковой логикой из меню, сочетания клавиш, кнопки и в будущем Plugin API. `Project Summary` отображает имя проекта, параметры Artboard и состояние сохранения. Не следует заводить `entities/project`, если это дублирует `SceneDocument` или `ProjectSession`.

### Web Viewer

Для цифрового сада предусмотрен облегчённый `SceneViewer`. Он получает `SceneDocument` и узкую функцию `resolveAsset`, читает опубликованный `project.json` и загружает ресурсы из `assets/`. В Viewer нет Electron, инструментов редактирования и файловых диалогов. Его можно встроить в Web App или публиковать как отдельную web-страницу.

## 10. Inspector и UI state

Inspector закреплён справа, открыт по умолчанию на широком окне; базовую ширину 264 px можно сохранить. Он не появляется и не исчезает при смене выделения.

- Без выделенного объекта показываются Scene Properties: ширина и высота Artboard, фон или прозрачность, read-only Scene ID.
- При выделенном объекте доступны свойства объекта и Scene вкладка.
- Для Rectangle показываются X/Y, Width/Height, вычисляемые X2/Y2, Fill, Stroke, Stroke Width, ID и тип.
- X2/Y2 вычисляются и не хранятся независимо от X/Y и размеров.
- Изменение размера Artboard не двигает и не масштабирует объекты; объекты за границами Artboard остаются в документе.
- View → Properties переключает панель. Предпочтение видимости сохраняется между запусками.
- Resize окна влияет на компоновку, но не меняет предпочтение пользователя; на узком окне допустим overlay.

Все изменения модели через Inspector проходят через операции Core. Визуальная тема редактора — Windows 95: серый фон, рельефные рамки, утопленные поля и компактные контролы.

## 11. Будущая расширяемость

Целевая возможность — читать и менять состояние редактора через документированный API, не взаимодействуя с React UI. Возможные API в будущем:

```ts
smys.objects.create(...)
smys.objects.update(...)
smys.objects.get(...)
smys.objects.delete(...)
smys.assets.import(...)
smys.assets.get(...)
smys.project.save(...)
smys.project.getInfo(...)
```

Будущий API должен быть версионируемым, валидировать команды, ограничивать разрешения и запрещать произвольную запись во внутренние структуры. Доступ к ресурсам контролирует Asset Storage, а не пути, переданные плагином. Чтение состояния позволяет проверить результат команды. UI, Plugin API и MCP должны использовать общие Core-операции и правила.

Публичный SDK не зависит от React и Electron UI. Пока не реализуются Plugin SDK, Command Bus, Event Bus, плагинный runtime или MCP-сервер. Проверка расширяемости проводится позже на тестовом host и conformance-тестах.

## 12. Порядок реализации

Ближайший продуктовый порядок — база редактора, перемещение, текст, PNG, прототип Win95 Code Card, минимальный API action-плагинов, внешний Code Card и путь установки/авторства с помощью AI. Актуальные статусы и критерии описаны в [ROADMAP.md](./ROADMAP.md).

Этот порядок не меняет архитектурные границы: проектные операции остаются в Application/Core, а сторонний код не получает привилегии Electron. Импорт изображений, Web Viewer и Browser Editor остаются отдельными сценариями и не являются зависимостями первого плагина.

Каждый этап — законченный пользовательский сценарий. Не следует реализовывать всю спецификацию одним изменением.

## 13. Проверки и критерии готовности

После каждого вертикального среза предусмотрены typecheck, ESLint, unit-тесты, интеграционные тесты Project Storage, Electron E2E сценария, Desktop build, Web build для затронутого web-сценария и проверка Git diff.

Для Project Storage особенно важны проверки:

- New → Save → Open и восстановление Artboard с объектами;
- отмена системного диалога;
- повреждённый манифест и несовместимая версия;
- ошибка записи и сохранность предыдущего документа;
- dirty state после изменения сцены;
- перенос проекта вместе с `assets/` после реализации импорта.

Core и Application должны тестироваться без React. Проверки запускаются по мере завершения срезов.

## 14. Ограничения текущего этапа

Без конкретного пользовательского сценария не добавлять:

- FSD для всего репозитория или массовый рефакторинг;
- дублирующую модель проекта;
- Use Case над каждой чистой операцией Core;
- глобальный Command Bus или универсальный Tool Engine;
- Electron API или браузерные файловые API в общих компонентах `src/editor`;
- дублирование Core или Editor UI между Desktop и Web;
- плагинный runtime, MCP-сервер и облачную синхронизацию;
- базу данных проектов или собственный файловый менеджер;
- несколько сцен и Artboards.

Приоритет — архитектурные границы и работающие сценарии, а не число слоёв и абстракций.
